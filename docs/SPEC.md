## 0. 概要

| 項目 | 内容 |
|---|---|
| アプリ名 | **Agnoria**（アグノリア） |
| 由来 | ギリシャ語 Agnoia（無知）＋ ローマの女神 Agenoria（子どもに学ぶ力を授ける）。「無知から学び始める」の意 |
| 目的 | TOEIC 450→600点帯の学習者が、スキマ時間に **単語** と **Part5形式の文法** を4択ドリルで繰り返す。**[v1.9]** **Part 2 形式の応答問題**（リスニング、3 択）も |
| 対象 | まず開発者自身。あわよくば App Store 公開 |
| 対応OS | **[v1.1]** iOS / iPadOS 27 以上（iPhone は縦画面のみ、iPad は全方向）/ macOS 27 以上（ネイティブ SwiftUI の1ターゲット。Mac Catalyst は使わない） |
| 通信 | 開発者のサーバーとは通信しない。全データをバンドル同梱。広告なし、課金なし、アカウントなし。**[v1.5]** 学習記録は iCloud で同期（計画）、**[v1.6]** 機能の利用回数とクラッシュ情報だけを Firebase（Analytics / Crashlytics）に送る（§7.1） |
| 商標回避 | アプリ名・Bundle ID・画面内の固定文言に「TOEIC」を使わない。App Store 説明文で「TOEIC対策に」と触れる程度は可 |

### 既存アプリへの不満（＝設計の軸）
- 「わかる／わからない」の自己申告は、自信のない単語を判定できない → **必ず4択で正誤が出る**
- 分野を狙って繰り返したい → **分野タイルから10問セットを何度でも**

## 2. データ

### 2.1 バンドルJSON

`Agnoria/Resources/Data/` 配下に `grammar.json` / `words.json` / **[v1.9]** `listening.json` を置く（synchronized folder なので Xcode に手で追加する必要はない）。起動時に SwiftData へ取り込む。

#### `grammar.json`（Part5 文法）
```json
{
  "id": "pos-001",
  "category": "品詞",
  "question": "The manager asked the team to submit their reports ______.",
  "question_ja": "部長はチームに、報告書を速やかに提出するよう求めました。",
  "choices": ["prompt", "promptly", "promptness", "prompted"],
  "answer": 1,
  "explanation": "動詞 submit を修飾するので副詞 promptly。-ly は副詞の目印。",
  "level": 500
}
```
- `answer` は `choices` のインデックス（0始まり）
- `category` は以下の5種（v1）: `品詞` / `前置詞・接続詞` / `語彙` / `時制・態` / `代名詞・関係詞`
- `level` は 450 / 500 / 550 / 600 の4段階（目安スコア帯）

#### `listening.json`（Part 2 形式の応答問題）**[v1.9]**
```json
{
  "id": "lis-wh-001",
  "category": "WH 疑問文",
  "question": "When does the store open on Sundays?",
  "question_ja": "日曜日は店は何時に開きますか。",
  "choices": ["At 10 a.m.", "Yes, it's open.", "On Main Street."],
  "choices_ja": ["午前 10 時です。", "はい、開いています。", "メイン通りです。"],
  "answer": 0,
  "explanation": "When で時を尋ねているので、開店時刻を答える At 10 a.m. が自然。Yes, it's open. は疑問詞の質問に Yes で答えていて、On Main Street. は Where への答え。",
  "level": 450
}
```
- 問いかけ 1 文と応答 3 つ（`choices`）。`answer` はインデックス。`choices_ja` は `choices` と同じ順の和訳
- `category` は問いかけの型 5 種: `WH 疑問文` / `Yes・No 疑問文` / `依頼・提案` / `平叙文` / `選択・付加疑問文`
- `explanation` は応答を A / B / C の文字で指さない（画面では順をシャッフルする）。英文をそのまま引いて説明する
- 音声データは持たない。問いかけと応答は端末の合成音声で読む（§6）
- 各帯 30 問（5 分野 × 6）。1 帯の問題数が単語（100）・文法（50）より少ないのは、音声の質を確かめてから増やすため

#### `words.json`（単語）
```json
{
  "id": "w-0001",
  "word": "invoice",
  "pos": "名詞",
  "meaning": "請求書",
  "examples": [
    { "en": "Please pay the invoice within 30 days.", "ja": "30日以内に請求書をお支払いください。" },
    { "en": "The invoice for the October order was sent to your accounting department.", "ja": "10 月分の注文の請求書を、貴社の経理部に送りました。" },
    { "en": "We cannot process the payment because the invoice number is missing.", "ja": "請求書番号が記載されていないため、お支払いを処理できません。" }
  ],
  "distractors": ["領収書", "見積書", "契約書"],
  "category": "ビジネス一般",
  "level": 450
}
```
- `distractors` は **意味が近い日本語の誤答3つ**（人手で作成。ランダム語は不可）
- `category` は以下の5種（v1）: `ビジネス一般` / `人事・採用` / `会議・連絡` / `店舗・顧客` / `混同しやすい語`
- `pos` は `名詞` / `動詞` / `形容詞` / `副詞` / `前置詞` / `接続詞`

#### 取り込みルール
- `id` を主キーに upsert。JSON側で問題文を修正したら次回起動時に反映される
- 学習履歴（正誤・ブックマーク）は `id` に紐づくので、問題を更新しても履歴は消えない
- JSON に存在しなくなった `id` は削除しない（履歴保護）。`isArchived = true` にして出題対象から外す。再び JSON に現れたら `isArchived = false` に戻す
- **[v1.1]** 取り込みは毎起動時にバックグラウンドで行うが、2ファイルの SHA-256 が前回取り込み時と同じならスキップする（UserDefaults に保存）

**[v1.5]** CloudKit に載せるための変更（§2.3）:
- `unique` 属性は使わない（CloudKit が対応しない）。`GrammarQuestion.id` / `Word.id` / `ItemProgress.itemID` の一意性は取り込みと取得のコードで保つ
- すべての保存プロパティに既定値を持たせる（`""` / `0` / `false` / `[]`）。optional にはしない
- ストアを 2 つに分ける。**問題ストア**（GrammarQuestion, Word。ローカルのみ、同期しない）と**記録ストア**（ItemProgress, StudySession。CloudKit 同期）。モデル間の参照は `itemID` 文字列だけなので分けられる

### 2.3 iCloud 同期 **[v1.5]**

目的: iPhone で進めた学習を iPad や Mac で続けられるようにする。Mac 版（§9）は同期が入ってから出す。

**方式（3 点セット）**
1. **自動同期**: SwiftData の `ModelConfiguration(cloudKitDatabase: .private("iCloud.com.himatsubu.Agnoria"))` で記録ストアを iCloud のプライベートデータベースに同期する。手動の同期ボタンは持たない（押し忘れと衝突解決の手間が増えるだけ）
2. **Debug と Release で環境を分ける**: Xcode から入れたビルドは CloudKit の Development 環境、App Store / TestFlight のビルドは Production 環境を使う（Apple の既定の挙動）。開発中のデータが本番の iCloud に混ざらない。Development 環境は CloudKit Dashboard でリセットしてよい
3. **同期オフの起動引数**: `-cloudSync NO` で記録ストアをローカルのみの構成にする。UI テストの `launchQuiet()` とシミュレータでの作業はこれで起動し、アプリを消せばデータが消える。ユーザー向けの設定項目にはしない

**同期する範囲**: ItemProgress と StudySession のみ。問題データは同梱 JSON から端末ごとに取り込む（iCloud に上げると端末ごとに二重になる）。設定（UserDefaults）は同期しない。到達帯（§3.4）は記録から再計算できるので、同期後に再計算して高い方に揃える

**ストアの構成 [v1.7]**: 記録ストアは 1.0 からの `default.store` をそのまま使い、これに CloudKit を付ける（既存の記録は初回同期でそのまま上がる）。問題データは新しい `questions.store`（ローカルのみ）に移し、初回起動で fingerprint を消して同梱 JSON から取り込み直す（`AppSettings.storesSplit`）。`default.store` から GrammarQuestion / Word の 2 モデルが外れるのは軽量マイグレーションで通る。記録を別ストアへコピーする案は採らない（コピーの失敗経路が増えるだけで、問題データの取り込み直しは 1 秒未満）

**モデルの制約 [v1.7]**: CloudKit では `@Attribute(.unique)` を使えず、全プロパティに既定値か Optional が要る。`ItemProgress.itemID` の unique を外し、各プロパティに既定値を付けた。同じ itemID の重複は取得時にまとめる（`RecordMerge`、`AppModel.mergeDuplicateRecords`）。StudySession の `id` も同様に取得時に 1 件へ寄せる

**衝突の規則**（2 台でオフラインに回答したときに起きる）
- 同じ `itemID` の ItemProgress が複数あれば、取得時にまとめる: `totalAnswered` が多い方を正、`isBookmarked` は OR、`recentResults` は `lastAnsweredAt` が新しい方、`totalCorrect` は正とした方の値。余った方は削除し、以後は 1 件に書く
- StudySession は追記のみで衝突しない。`id`（UUID）が同じものが 2 件あれば 1 件に寄せる
- 同じレコードを両方が書き換えた場合は CloudKit の後勝ち。学習記録として許容する（1 セットぶんの回答が消えることがある）

**更新経路**: 1.0 のローカルストアに同期を足す。初回起動で既存レコードがそのまま上がることを、1.0 を入れた端末からの更新で確認する。CloudKit Dashboard でスキーマを **Production に配備してから** リリースする（配備を忘れると本番で同期されない）

**iCloud が使えないとき**（未サインイン、iCloud Drive オフ、機内モード）: 今までどおりローカルで動く。同期は復帰後に再開する。エラーは出さない

**同期後の整合 [v1.7]**: 他端末からの変更は `NSPersistentStoreRemoteChange` で受け、1 秒まとめてから、重複の合成 → 到達帯の再計算（`Stage.unlockedFromRecords`、高い方に揃える）→ ウィジェットの写しの書き直し、の順に行う（`AppModel.reconcileAfterSync`）。起動時の取り込みの後にも同じ合成を行う

**entitlement と起動 [v1.7]**: CloudKit コンテナの entitlement が無いビルドで同期の構成を開くと、throw ではなく後で別スレッドで落ちる（CKContainer の例外）。そのため同期を切る手段は起動引数 `-cloudSync NO` と、ユニットテストのホストとして起動したとき（`XCTestConfigurationFilePath` がある）の 2 つで、entitlement は必須

**文言の変更**: プライバシーポリシーとサポートページの「端末内にのみ保存」を「端末と、お使いの iCloud に保存されます。開発者が見ることはできません」に直す。App Store の「App のプライバシー」は「データを収集しない」のまま（プライベートデータベースは利用者自身の領域）。ストアの説明文の「通信なし」は「開発者のサーバーとの通信なし」の意味で残すが、「学習の記録は iCloud で同期」を 1 行足す

**設定画面**: 「iCloud 同期」の行に状態だけ出す（同期中 / 未サインイン）。トグルは持たない。「学習履歴をリセット」は iCloud 側も消える旨を確認文に書く

**権限と設定**: Signing & Capabilities で iCloud（CloudKit、コンテナ `iCloud.com.himatsubu.Agnoria`）と Background Modes（Remote notifications）。Xcode の自動署名で足りる

## 3. 出題ロジック

### 3.1 単語の出題形式（1語から3形式を自動生成）

| 形式 | 問題 | 選択肢 | 誤答の出どころ |
|---|---|---|---|
| `meaning` 意味を選ぶ | `invoice` | 請求書 / 領収書 / 見積書 / 契約書 | `distractors` |
| `cloze` 例文穴埋め | `Please pay the ______ within 30 days.` | invoice / receipt / estimate / contract | 同じ `pos`・同じ `level` の他の単語から3語をランダム抽出 |
| `jaToEn` 日→英 | 請求書 | invoice / receipt / estimate / contract | 同上 |

- **[v1.7]** 例文は 1 語につき 3 つ（`examples`。1.0 の `example` / `example_ja` は 1 つ目として残した）。出題のたびに 3 つから 1 つをランダムに選び、`cloze` はその文を空欄にし、`meaning` / `jaToEn` でも解説と読み上げにその文を使う。同じ文を見るだけで答えが分かる丸暗記を避け、使われ方の幅を見せるため。3 つすべてで穴埋めが作れることをデータ検証で保証する
- `cloze` は選んだ例文中の `word` を `______` に置換。**[v1.1]** 完全一致（大文字小文字無視）→ 規則的な語尾変化（-s/-es/-ed/-d/-ing/-ly、-e 脱落、-y→-ies、子音重ね）の順に探す。単純な先頭一致はしない（`in` が `invoice` に化けるため）。見つからなければその語は `meaning` 形式で出す
- 誤答抽出は **[v1.1]** 同 `pos`・同 `level` → 同 `pos` → 全単語 の順に条件を緩める。自分自身・同じ綴り・同じ `meaning` の語は除く

### 3.2 セット生成（10問）

```
入力: mode（nil = おまかせ [v1.2]）, category（nilならミックス）, format（単語のみ）
1. 対象 = isArchived == false かつ mode 一致（おまかせなら単語・文法の両方）かつ category 一致（ミックスなら全件）
2. 優先度スコアを付ける（d = 最後に答えてからの経過日数 / 14 を 0〜1 に丸めたもの [v1.2]）
     未回答:                    3
     直近3回に不正解あり:       2 + (不正解の数)
     直近3回すべて正解:         0.3 + 1.2 × d   ← 「卒業」。除外はしない。2週間放置で 1.5 まで戻る
     それ以外:                  1   + 0.5 × d
     [v1.4] 過去に習得済み（masteredAt あり）の問題は、直近が正解なら「卒業」の重み、直近が不正解なら「不正解あり」の重み
3. スコアを重みにして重み付きランダムで10件抽出（重複なし）
4. 各問の選択肢の並びをシャッフル。正解のインデックスを記録
```

- **[v1.2]** おまかせ（`QuizConfig.auto`）は単語・文法の全分野を1つの候補群にして上の手順で抽出する。単語の形式は1問ごとにランダム。「何を勉強するか」をユーザーが選ばなくて済むのが目的。未回答が最優先、次に間違い、放置した卒業問題は時間とともに復習に回る。**[v1.9]** リスニング（§3.5）はおまかせと、ホームの復習（間違えた / ブックマーク。`mode = nil`）には入れない（`DrillMode.autoModes`）。音を出せない場面で突然音声の問題が出ると答えられないため。分野画面でリスニングを選んだときだけ出す
- **[v1.2]** 習得段階（`Mastery`）: 未学習（未回答）/ 苦手（直近3回に不正解）/ 学習中（それ以外）/ 習得（直近3回すべて正解）。優先度と同じ判定を4段階に写しただけで、ロジックは持たない。「復習待ち」= 習得後 7 日以上経過
- **[v1.4]** 一度習得した問題の扱い: はじめて3連続正解した日時を `ItemProgress.masteredAt` に残す。以後その問題は **直近の1回が正解なら習得**（3連続を待たない）、直近が不正解なら「学習中」（苦手には落とさない）で、次のセットに優先的に出る（重みは不正解と同じ）。復習で1回ミスしただけで未学習相当に落ちると、全体の習得率が 97〜99% で頭打ちになる（シミュレーションで確認）ため。更新前から習得していた問題には、起動時に最後の回答日時を `masteredAt` として補う（`AppModel.backfillMasteredAt`）
- 対象が10件未満なら、あるだけ出す（最低1件）
- 「間違えた問題だけ」モード: 直近3回に不正解を含むもののみ
- 「ブックマークだけ」モード: `isBookmarked == true` のみ

### 3.4 ステージ **[v1.3]**

「何を勉強すべきか」をさらに絞るため、スコア帯を 450 → 500 → 550 → 600 の順に進む。

- **到達帯** `unlockedLevel`（UserDefaults、初期値 450）。出題対象は到達帯以下のレベル（おまかせも分野タイルも）
- **今の帯** = 到達帯以下で未クリアの最も低い帯。すべてクリア済みなら到達帯
- **クリア** = その帯の全問題（単語＋文法）のうち習得（直近3回すべて正解）が **80%** 以上
- セット完走時に到達帯がクリアされていれば次の帯を開く。結果画面で知らせる。**[v1.5]** 開く前に専用の演出画面を挟む（§4.3.1）。最上位 600 をクリアしたときは開く先が無いが、演出だけ 1 回出す（`topStageCelebrated`。履歴リセットで戻る）
- おまかせの重みは §3.2 のスコアに係数を掛ける: 今の帯 ×1、それ以外の到達済み帯 ×0.35（復習として少し混ざる）、未到達 ×0
- 下の帯の習得率が落ちれば「今の帯」はそこへ戻る（到達帯は下がらない）
- 設定で到達帯を手で変えられる（先に進む・戻る）。履歴リセットで 450 に戻る

**軸ごとの帯 [v1.8]**: 上の決まりはすべて、出題の種類（`DrillMode`: 単語 / 文法 / **[v1.9]** リスニング）ごとの **軸** で別々に適用する。
- 到達帯は軸ごと（`unlockedLevel.word` / `unlockedLevel.grammar` / `unlockedLevel.listening`）。クリアは「その軸のその帯の問題の 80%」（単語は 1 帯 100 語、文法は 50 問、リスニングは 30 問）。最上位の演出も軸ごとに 1 回（`topStageCelebrated.word` など）
- 出題対象は軸ごとの到達帯まで。おまかせの重みも、問題の軸の今の帯・到達帯で決める（軸の配分は優先度の重み任せ。決め打ちの比率は持たない）
- セット完走時は、そのセットで出した軸だけクリアを判定する。2 軸を同時にクリアしたら演出は 1 画面にまとめる（§4.3.1）
- 理由: 合算だと習得率はほぼ単語で決まり、文法が得意でも単語が追いつくまで進めない。また種類を足す（リスニングなど、Issue #30）ときに既存の軸の習得率を崩さず、軸を 1 本増やすだけで済む。同じ種類の問題を増やすとその軸の習得率は下がる（軸を分けても避けられない）
- 移行: 1.2 までの合算の `unlockedLevel` は使わない。1.8 の初回起動で記録から軸ごとに求め直し（`Stage.unlockedFromRecords`、`stageTracksMigrated`）、古いキーを消す。利用者がまだ少ないので手動で変えた到達帯は引き継がない
- iCloud 同期後の再計算（§2.3）も軸ごと

### 3.5 リスニング（Part 2 形式の応答問題）**[v1.9]**

短い問いかけ（または発言）を聞き、3 つの応答から最も自然なものを選ぶ。問いかけと応答は **音声だけ** で出し、文字は回答のあとに出す。

- データは `listening.json`（§2.1）。応答の並びはセットごとにシャッフルし、和訳も同じ順に並べ替える（`ListeningQuestionFactory`）
- 音声は端末の合成音声（`AVSpeechSynthesizer`）。問いかけ → 0.9 秒 → 応答 1 → 0.9 秒 → 応答 2 → 0.9 秒 → 応答 3 の順に読む。問いかけと応答で別の声、発音は問題ごとに en-US / en-GB / en-AU から決定的に選ぶ（§6）。録音は持たない（オフラインで動き、アプリのサイズも増えない。質が足りなければ録音に替える判断は SPEC-REVIEW N1）
- 出題の候補・優先度・習得・帯のクリアは単語・文法と同じ（§3.2〜3.4）。軸は `listening`
- おまかせと復習には混ぜない（§3.2）。分野画面（§4.7）の「リスニング」セグメントから、分野タイルかミックスで始める
- 速度は設定の「読み上げの速度」と共通（§4.4）

iOS のホーム画面に置く WidgetKit のウィジェット（ターゲット `AgnoriaWidgetExtension`、Bundle ID `com.himatsubu.Agnoria.AgnoriaWidget`）。読み取り専用で、タップするとアプリが開く。Mac には出さない（依存と埋め込みは `platformFilters = ios`）。

| サイズ | 表示 |
|---|---|
| small | 連続日数（炎のアイコン + 日数）と「今日も学習済み / 今日はまだ」。ホームの StreakCard と同じ内容 |
| medium | 左に small と同じ、右に ~~今の帯（「500 点帯」「42% 習得」+ 進捗バー）と 4 帯の並び~~ **[v1.8]** 軸ごとに 1 段（「単語 500 点帯 42%」+ 進捗バー + 4 帯の記号。StageChips と同じ記号: クリア ✓ / 今の帯 ◉ / 開いている ○ / 未到達 🔒）。**[v1.9]** 3 段（単語 / 文法 / リスニング） |
| 写しが無いとき | 「アプリを開いて、今日の 10 問から」（インストール直後、まだアプリを開いていない） |

**データの受け渡し**: 拡張はアプリのストアを開かない。アプリが `WidgetSnapshot`（最後に学習した日、その日を最終日とする連続日数、**[v1.8]** 軸ごとの `Track`（軸名、到達帯、今の帯、帯ごとの習得率とクリア済みか））を App Group `group.com.himatsubu.Agnoria` の UserDefaults に JSON で書き、`WidgetCenter.reloadAllTimelines()` を呼ぶ。書くのは起動時（取り込みの後）、セット完走、履歴リセット、設定で到達帯を変えたとき。型は `Shared/WidgetSnapshot.swift` でアプリと拡張の両方に入れ、写しを作る関数（Stage / Streak を使う）はアプリ側（`Agnoria/Logic/WidgetSnapshot+Make.swift`）。

**日付の扱い**: 「今日やったか」と「連続日数」は拡張側で `lastStudyDay` から判定する（最終日が今日なら学習済み、今日か昨日なら連続は続いている、それより前なら 0）。タイムラインは「今」と「次の 0 時」の 2 エントリで、0 時を過ぎると「今日はまだ」に戻る。iCloud 同期（§2.3）で他端末から記録が来たときは、アプリの次回起動で写しが書き直される。

**見た目**: `containerBackground(.fill.tertiary)`、主な数字と文は `widgetAccentable()`（色合い調整でも読める）。Dynamic Type は標準に任せる。「1 問だけ」の対話型ウィジェットは別 Issue（§9）。

### 4.8 App Store の評価 **[v1.8]**

StoreKit の `requestReview`（SwiftUI の `@Environment(\.requestReview)`）で OS の評価ダイアログを頼む。実際に出すか、何回まで出すか（1 年に 3 回まで）は OS が決める。独自のダイアログやレビューのお願いの文言は出さない。

- **頼むきっかけ**（セット完走時に `ReviewPrompt.trigger` で判定）: そのセットでスコア帯をクリアした（`stage_clear`）、または累計の完走セットが 5 以上で正答率 80% 以上（`high_score`）
- **頼む場所**: 結果画面を開いて 1.5 秒後。帯クリアのときは演出を見終えた後の結果画面。その前に画面を離れたら頼まない（セット中・起動直後・成績の悪い結果画面では頼まない）
- **頻度**: 同じバージョン（`CFBundleShortVersionString`）では 1 回だけ（`AppSettings.reviewRequestedVersion`）
- **設定**: 「このアプリについて」に `App Store でレビューを書く`（`https://apps.apple.com/app/id6823061416?action=write-review` を開く）
- **計測**: 頼んだとき `review_requested`（trigger）、設定のリンク `review_link_opened`。ダイアログが実際に出たか・評価したかは OS から取れない
- 起動引数 `-reviewPrompt NO` で頼まない（UI テストはこれで起動）。Debug ビルドではダイアログが出るが送信されない。TestFlight では出ない（OS の仕様）ので、確認は Debug で起動引数 `-debugReviewPrompt YES`（条件に関係なく毎セット頼む）を使う

### 4.9 学習のリマインダー通知 **[v1.8]**

その日にまだ 1 セットも完走していなければ、決めた時刻にローカル通知で知らせる（`UNUserNotificationCenter`。サーバーは使わない）。iOS と Mac で同じ。

- **予約のしかた**: 通知の時点で「今日やったか」を判定できないので、繰り返し通知は使わない。今日から 7 日分を 1 日 1 件ずつ予約し（`Reminder.plan`、識別子 `reminder-yyyy-MM-dd`）、起動・セット完走・履歴リセット・iCloud 同期後・設定の変更のたびに置き換える。今日もう完走していれば今日の分は予約しない。時刻を過ぎた分も予約しない
- **文面**: 連続中なら「連続 N 日 / 今日の 10 問で N+1 日目。3 分で終わります」。今日の分は昨日までの連続、明日の分は今日完走していれば今日までの連続で数え、それより先や連続が 0 のときは「今日の 10 問 / 1 セット 3 分。今日の分を始めましょう」
- **許可**: 起動直後には求めない。最初のセットを完走した結果画面で 1 回だけ（1.5 秒後。その回は評価ダイアログ §4.8 を重ねない）、または設定でオンにしたときに OS のダイアログを出す（`reminderPrompted`）。許可されたらオン、拒否ならオフ
- **設定**: 「リマインダー」セクションに `学習のリマインダー`（既定オフ。許可でオンになる）と、オンのとき `時刻`（既定 20:00、`reminderMinutes`）。拒否されていれば「通知が許可されていません」と `通知の設定を開く`（OS の通知設定）
- アプリを使っている最中は出さない（`willPresent` で表示しない）。通知をタップするとアプリが開く（画面は変えない）
- iCloud 同期で他の端末で学習した分は、同期の取り込み後か次の起動で予約し直したときに反映する
- **計測**: `reminder_permission`（granted）、`reminder_opened`、`settings_changed`（reminderEnabled / reminderTime）
- 起動引数 `-reminderPrompt NO` で許可を尋ねない（UI テストはこれで起動）。`-reminderMinutes 1230` で時刻を上書きできる（確認用）。テスト中は通知センターに触れない

### 7.1 利用状況の計測とクラッシュ報告 **[v1.6]**

目的: どの機能がどれだけ使われているか（セット数、モードや分野の偏り、帯クリアまでの道のり、Apple Intelligence・読み上げ・ブックマークの利用、途中離脱）を知る。App Store Connect の App Analytics（DL・セッション・継続率）だけでは分からないアプリ内の動きを補う。

**送る先**: Firebase Analytics と Crashlytics（SPM `firebase-ios-sdk` の `FirebaseAnalyticsCore` / `FirebaseCrashlytics`。Core は IDFA 対応（IdentitySupport）と広告の端末内コンバージョン計測を含まない版で、import は同じ `FirebaseAnalytics`。Analytics の要件で `OTHER_LDFLAGS` に `-ObjC`）。アプリ側は `UsageAnalytics` に集約し、View は Firebase を直接呼ばない。

**クラッシュ報告**: Xcode の Organizer は「開発者と共有」を許可した人の分しか、日単位でしか届かないので Crashlytics で補う。クラッシュに加えて、握りつぶしていた失敗（SwiftData の保存失敗 `save.answer` / `save.session` / `save.bookmark` / `save.backfill`、取り込み失敗 `import`）を非致命エラーとして `record(error, where)` で送る。シンボル化のため Xcode Cloud のアーカイブ後に `ci_scripts/ci_post_xcodebuild.sh` が `upload-symbols` で dSYM を送る（アーカイブ以外のアクションと plist の無いビルドでは何もしない）。

**送るもの**（問題の内容・回答・個人を特定できる情報は送らない）

| イベント | パラメータ |
|---|---|
| `set_start` | mode（auto / word / grammar / listening **[v1.9]**）, category（分野 id か mix）, format（meaning / cloze / jaToEn / random）, filter（all / wrong / bookmarked / retry） |
| `set_finish` | 上に加えて count, correct, duration_sec |
| `set_abort` | 上に加えて answered |
| `stage_clear` | mode（word / grammar / listening）**[v1.8]**、level, next（最上位は 0） |
| `rephrase_used` / `practice_used` / `speak_tapped`（手動の読み上げのみ） | なし |
| `replay_tapped` | なし **[v1.9]**（リスニングの `聞く` / `もう一度聞く`。自動再生は数えない） |
| `bookmark_toggled` | on |
| `history_reset` | なし |
| `settings_changed` | key（soundEffects / autoSpeak / speechRate / unlockedLevel.word / unlockedLevel.grammar / unlockedLevel.listening / reminderEnabled / reminderTime） |
| `review_requested` | trigger（stage_clear / high_score）**[v1.8]** |
| `review_link_opened` | なし **[v1.8]** |
| `reminder_permission` | granted（1 / 0）**[v1.8]** |
| `reminder_opened` | なし **[v1.8]** |

ユーザープロパティ: ~~`unlocked_level`~~ **[v1.8]** `unlocked_level_word` / `unlocked_level_grammar` / **[v1.9]** `unlocked_level_listening`。Firebase が自動で集める `first_open` / `session_start` / `screen_view` はそのまま。1 問ごとの回答イベントは量が多いので送らない。IDFA は使わない（`FirebaseAnalyticsCore` を使い AdSupport も IdentitySupport もリンクしない。ATT のダイアログは出さない）。

**送らない条件**（優先順）
1. 同梱の `GoogleService-Info.plist` が無い（Firebase 未設定のビルド）
2. 起動引数 `-analytics NO`（UI テストの `launchQuiet()` が付ける）。Debug ビルドは逆に `-analytics YES` を付けたときだけ送る（開発中の操作を本番の計測に混ぜない。DebugView で確認するときは `-FIRDebugEnabled` も付ける）

利用者向けのオプトアウト（設定のトグル）は持たない。Apple の要件ではなく、「App のプライバシー」の申告とプライバシーポリシーで足りる（配信は日本のみ）。

**確認用のクラッシュ**: Debug ビルドだけ、起動引数 `-debugCrash YES` でホーム表示直後に `fatalError` で落ちる。報告は次回起動時に送られるので、落とした後に `-analytics YES` でもう一度起動する。Crashlytics コンソールのオンボーディングは最初の報告が届くまで終わらないので、導入時に 1 回これで送った

**設定ファイル**: `GoogleService-Info.plist` は `Agnoria/` に置いてリポジトリにコミットする（synchronized folder なので置くだけでバンドルされる）。中身（API キー、プロジェクト ID、App ID）は Google が公開情報として扱うもので、アプリに同梱される以上は隠せない。使うのが Analytics だけなので、第三者にできるのは偽のイベントを送ることまで。Google Cloud コンソールでこの API キーに iOS アプリ（Bundle ID）の制限を付けておく。GitHub の secret scanning の警告は閉じる。

**申告と文言**: App Store Connect の「App のプライバシー」は「データを収集しない」から、「使用状況データ（製品の操作）」「診断（クラッシュデータ）」「識別子（デバイス ID）」を「分析」目的で収集・ユーザーに紐付けない・トラッキングに使わない、に変える。`PrivacyInfo.xcprivacy` は Firebase SDK 側のマニフェストが収集種別を申告するので、アプリ側は触らない。プライバシーポリシー・サポートページ・ストア説明文・ランディングページの「通信なし」「解析ツールなし」を直す（§1）。

## 8. 問題データの作り方（開発者向け）

- **すべてオリジナル問題**。市販問題集・公式問題集・単語帳の例文・解説の転載、言い回しを変えただけの改変は不可
- 単語リスト自体（頻出語）は事実情報なので使ってよい。例文・和訳・誤答を自作する
- 初期目標: 文法 5分野 × 50問 = 250問、単語 5カテゴリ × 50語 = 250語。動いたら各100まで増やす
- 初期データ **[v1.1]**: `grammar.json`（文法30問。5分野×6問、自作）、`words.json`（単語50語。旧 `words_sample.json`）
- **[v1.3]** 単語 400（各スコア帯 100、各カテゴリ 80）、文法 200（各スコア帯 50、各分野 40）。既存の 80 問はそのまま残し、残りは Claude がスコア帯ごとに書いた（未レビュー）。単語の綴りは全体で一意。検証スクリプトでチェックした項目: 形式・id の重複・綴りの重複・穴埋めが作れること・誤答が意味と重複しないこと・正解位置の偏り・「TOEIC」不在
- **[v1.9]** リスニング 120（各スコア帯 30、各分野 24）。Claude が帯ごとに書き、別のレビュー担当に「正解が 1 つだけ自然か」「誤答が Part 2 の典型（似た音・語の繰り返し・疑問詞の取り違え・Yes/No の誤用・時制や主語のずれ）になっているか」「和訳」「合成音声で読みにくい表記（略語・記号）が無いか」を検査させてから取り込んだ。解説は応答を A / B / C で指さない（テストで保証）
- 生成は Claude Code に任せてよいが、以下をチェック:
  - 正解が一意であること（他の選択肢でも文法的に成立しないか）
  - `distractors` が意味的に近いこと
  - `level` が 450〜600 の帯に収まっていること（難語・専門語は入れない）
